# 整合性チェックの一周(標準手順)

## 役割
- NO3: 起動(「見て」)、承認、検収、DECISIONS の記入
- MUSE: 入口(依頼の登録)と出口(配置・運搬・検収一覧)。内容の判断と構造化はしない
- Claude: 現物チェックと構造化。書くのは results/checks/ への新規ファイル、
  status の detection_result と last_checked、gate_log への1行追記のみ
- GPT: 読んで作る席。MSG番号は仮番号で返す
- Actions: 機械でできる検証(type、message_id 重複、書式)を担う

## 手順
1. 登録(MUSE): 封筒の type は request・question・reply・report の4種類。
   必須項目(goal_id を含む)が揃うまで登録しない。番号は MUSE だけが付ける。
2. 起動(NO3): 「見て」と指示する。
3. 事前チェック(Claude): handoff/CURRENT.md など対象のファイルだけを読む。全量は読まない。
   各項目を「一致 / 不一致 / 確認不能」の3区分で、現物の該当箇所を添えて
   results/checks/YYYY-MM-DD_題名.md に新規ファイルで置く。
4. 承認(NO3): 不一致の扱いを決める。承認の範囲は、MUSE への指示に明記する。
5. 修正(MUSE): 承認の範囲内だけを直す。関連する変更(ファイル名・封筒・参照元)は
   1コミットにまとめる。過去の gate_log は書き換えず、新規1行で残す。
   修正の前後に、開始と終了を gate_log に1行ずつ書く。
6. 事後チェック(Claude): 修正が承認範囲内か、漏れがないか、
   router と state-check が緑かを現物で確認し、同じく results/checks/ に置く。
7. 検収(NO3): 事後チェックの結果を見て OK / 保留 / 却下を決める。

## 完了条件
- message-router と state-check の run が緑
- INDEX の末尾が「検証結果:問題なし」
- 承認範囲外の変更がない(事後チェックで確認済み)

## 原則
- 判断の根拠は現物だけ。確認できないものは「確認不能」と書き、推測で補わない。
- 書く席と確認する席を分ける。MUSE の報告は、MUSE 自身では確認済みにしない。
- 機械でできる突き合わせは、AI の読み取りに任せず、スクリプトと Actions に任せる。
- 引き継ぎでは、全体を読み直さず、引き継ぎ票と指定のファイルだけを読む。
- 承認範囲を超える変更が必要になったら、修正せず止まって NO3 に報告する。
- 履歴の書き換え(--reset-author、rebase、強制push)は、NO3 が明示した場合のみ。
- main への反映は、NO3 が決めたときのみ。
