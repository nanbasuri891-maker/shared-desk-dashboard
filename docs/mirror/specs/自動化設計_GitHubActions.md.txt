# 自動化設計：GitHub Actions を実行基盤にする（2026-11-03 MUSE 作成・同日 NO3 承認、実装開始）

目的：NO3 が間に入って仕事をつなぐ状態を解消し、GitHub 上のタスク状態をトリガーに次の工程が自動で進む仕組みを作る。NO3 の介入は、人間の判断・承認が必要な場面だけに限定する。

## 1. 確認した事実（2026-11-03 実測）

- 机のリポジトリに `.github/workflows` はまだ無い。GitHub Actions の有効状態と実行履歴は、現在 MUSE が使っているトークンの権限では読めなかった（403。Actions 系の権限が範囲外）。
- `tasks/` にはタスク JSON の形式（スキーマ v0.2）と実例が既にある。ただし「作成後は編集しない」設計で、状態（status）の欄がない。状態の置き場は別に必要。
- 作業は `ai/` ブランチ群で行われている。push をトリガーにするワークフローは、そのブランチに置いたファイルで動くため、main を触らずに始められる。
- GPT の現在環境：通常の ChatGPT の会話＋GitHub 連携で机を読む。GitHub Actions から GPT の会話を起動する手段はない。API で呼ぶ場合は別の環境・別の文脈になる。
- Claude の現在環境：NO3 が会話で「見て」と言うと起動し、机を読んで成果物を机に置く。Actions から起動する手段はない。API 等への置き換えは席そのものの変更になる。
- MUSE の現在環境：定期実行の仕組みがあり（週次チェックの実績あり）、机の状態を見て自分の工程（照合・確定・整形・記録）を実行できる。ただし GitHub API 接続が不安定なことがある。
- Discord（美脳）への Webhook 投稿は実績あり。Actions からも Webhook 経由で通知できる（URL をリポジトリの Secrets に登録する必要あり）。

## 2. 設計（状態駆動）

### 状態の置き場
- タスク JSON（不変の発生記録）とは別に、案件ごとの状態ファイルを持つ。置き場の候補：`tasks/status/<案件ID>.json`（編集可能なのはこのファイルだけ）。
- 状態ファイルの形式（案）：

```json
{
  "case_id": "aida_no1",
  "title": "アイダ投稿生成の下ごしらえ（第1号）",
  "ip": "aida",
  "status": "prompt_locked",
  "updated_at": "2026-11-03T00:00:00+09:00",
  "updated_by": "muse",
  "links": {
    "draft": "proposals/gpt/（原案がある場合のみ）",
    "final": "goals/meta-routing/REQUEST_to_claude_aida_no1_2026-11-02.md",
    "deliverable": "results/（納品後に記入）"
  },
  "blocked_reason": null,
  "history": [
    { "from": "draft_ready", "to": "prompt_locked", "by": "muse", "at": "日時", "note": "照合・確定の内容を1行" }
  ]
}
```

- 状態の値と、遷移を書ける担当を固定する。

| 状態 | 意味 | 次に動く担当 | 遷移を書く |
|---|---|---|---|
| draft_required | 原案が必要 | GPT（壁打ち） | MUSE |
| draft_ready | 原案が置かれた | MUSE（照合・擦り合わせ） | Actions（原案の着地を検知） |
| prompt_locked | 確定版が置かれた | Claude | MUSE |
| execution_completed | 納品が机に上がった | MUSE（検証・整形） | Actions（完備チェック後） |
| human_approval_required | NO3 の承認待ち | NO3 | MUSE |
| blocked | 判断が必要で停止中 | NO3 | 誰でも（理由を必須で書く） |
| done | 完了 | ― | NO3 の承認後に MUSE |

### GitHub Actions がやること（判断はしない。機械処理だけ）
1. 状態ファイルと関連パスの変更（push）を検知する。
2. 状態遷移が許可された組み合わせかチェックする（飛び級や逆行があれば blocked にして知らせる）。
3. 成果物の完備チェック：納品ファイルに必須の見出し（読み込み報告・参照指定など）があるかを見る。
4. 状態の一覧サマリを更新する。
5. 通知は独立した差し替え可能な段として分離する（2026-11-03 NO3 の注意）。必須ではない。以前 Discord への自動投稿で問題があったため、第1段階では通知は無効のまま置き、使う場合も状態チェック本体とは分けたジョブにする。通知先・手段は後から差し替えられる形にする。

なお、「Claude の納品を検知して状態を進める」ことと「Claude に自動で仕事を渡す」ことは別であり、第1段階では後者は行わない（2026-11-03 NO3 の注意）。Claude への仕事の受け渡しは、従来どおり NO3 の「見て」が起点。

### MUSE がやること（定期実行で状態を見る）
- draft_ready を見つけたら、正本・仕様との照合と擦り合わせを行い、確定版を置いて prompt_locked へ進める。
- execution_completed を見つけたら、読み込み量・翻訳の抜け・品質を検証し、整形して human_approval_required へ進める。
- MUSE の接続が落ちていても、状態は机に残るので壊れない。復旧後に続きから進む。中継を MUSE 一点に寄せないため、検知と通知は Actions 側に置く。

### GPT・Claude の工程（第1段階では現行の起動方法のまま）
- GPT：NO3 との壁打ちで原案を作る。原案が proposals/gpt/ に置かれたら Actions が検知して draft_ready へ進める（格納は MUSE）。
- Claude：NO3 の「見て」で起動する。prompt_locked になったことは状態サマリで見える形にし、通知を使うかどうかは通知の段を有効化した後の話とする（第1段階では通知なし）。
- API 化は第2段階の判断事項。やる場合は、API キーの用意と、席に蓄積した文脈をどう渡すか（文脈パックの設計）が前提条件になる。

### NO3 の介入点（第1段階の到達点）
1. GPT との壁打ち（原案の起点）
2. Claude への「見て」
3. human_approval_required での承認
4. blocked の判断

## 3. 実装作業の分解（第1段階）

| # | 作業 | 担当 | 前提・条件 |
|---|---|---|---|
| 1 | 状態ファイルの形式と遷移表を確定する | MUSE 作成 → NO3 確認 | 本設計の承認 |
| 2 | Actions ワークフロー v1（遷移チェック＋完備チェック＋サマリ更新＋Discord 通知）を配置する | MUSE | リポジトリで Actions が有効なこと。Discord Webhook URL の Secrets 登録（NO3 の操作） |
| 3 | MUSE の定期 watcher（状態を見て自分の工程を進める）を新設する | MUSE | NO3 の承認 |
| 4 | 第1号に状態ファイルを付け、状態遷移が実際に流れるか実走する | MUSE＋NO3 | 2 と 3 の完了後。第1号の依頼文自体は変更しない |
| 5 | 実走の記録（声かけの回数、止まった箇所）を残し、第2段階（API 化の可否）の判断材料にする | MUSE | 4 の完了後 |

## 4. 障害となる点・未確認

- リポジトリで GitHub Actions が有効かどうかが未確認（トークンの権限外のため、設定画面でしか分からない）。NO3 に確認してもらう必要がある。
- 現在のトークンは Actions 系の権限を持たない。ワークフローファイルの配置自体は contents の書き込みで可能だが、有効化の確認は NO3 の操作になる。Secrets の登録は、通知の段を有効化する場合にのみ必要（第1段階では不要）。
- GPT・Claude を API 化すると、席に蓄積した文脈が切れる。第1段階では触らない。
- Dify を制御に使う案は、API キーの保管問題（O-001）が未解決のため、第1段階では採用しない。
