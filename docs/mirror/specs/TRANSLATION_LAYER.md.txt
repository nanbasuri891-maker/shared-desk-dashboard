# TRANSLATION_LAYER.md
## マクロハーネスAI｜翻訳層専用指示書＋チェックリスト

文書区分：共通基盤・実行規約  
適用対象：MUSE（主担当）、必要に応じて全エージェント  
優先順位：各エージェント固有の指示より上位（ただし最上位GOAL・承認ルールに従う）  
更新ルール：人間（NO3）の承認を経てのみ改訂する。実行結果で自動書き換えしない。

---

## 1. 翻訳層の目的

人間向けの構造説明・構想文書・会話メモを、  
各AIエージェントが**即実行できる手順・指示・成果物形式**に変換する層である。

翻訳層は「誰が毎回翻訳するか」の問題ではなく、  
**変換ルールとチェック基準を正本として固定し、担当エージェントが読み込んで動く**ための仕組みである。

---

## 2. 翻訳の基本原則

1. **抽象度を落とす**  
   概念・方針・思想を、エージェントが今日実行できる具体的な手順に変換する。  
   例：  
   - 概念：「SNSは機会損失を防ぐためのプラットフォームである」  
   - 手順：「X投稿を生成する際、受け手のHARM（Health / Ambition / Relation / Money）のどれを塞ぐ接点かを一文で明示してから生成する」

2. **FACTを区別する**  
   - 確認済み事実  
   - 仮説  
   - 未確認事項  
   を必ず分けて書く。不足情報を勝手に補完しない。

3. **エージェント別に分解する**  
   同じ概念でも、出力形式はエージェントごとに異なる。  
   - Grok（X運用）：対象・現状・仮説・提案仕様の4項目  
   - Claude（バッチ）：実行可能なタスク指示＋完了条件  
   - GPT（画像）：サイズ・画質・参照画像・禁止事項  
   - MUSE自身：橋渡し先・影響確認項目

4. **実行可能性を最優先する**  
   「良い説明」ではなく「今すぐ動ける指示」にする。  
   空欄や曖昧な表現が残っている状態で渡してはならない。

5. **正本と実行記録を分離する**  
   翻訳結果は実行記録またはCLAUDE_STATE等に書く。  
   翻訳層の指示書自体を実行結果で上書きしない。

6. **短くする**  
   指示は必須事項だけを命令形で書き、説明は削る。長い指示は、読む側の読み込み量を増やし、起動の失敗と読み漏らしの原因になる（2026-11-03〜04 の実測。Grok のカスタム指示案の原則と、Claude の起動失敗への対処から）。  
   条件の網羅は、文章を長くすることではなく、必要な材料をパッケージに同梱することで担保する。

---

## 3. 翻訳の標準手順（MUSEが従う）

1. 人間向け文書・会話・見立てを読む  
2. 対象エージェントとGOALを特定する  
3. 概念を手順に落とす（抽象度変換）  
4. FACT・仮説・未確認を明示する  
5. エージェント別の出力形式に合わせる  
6. チェックリストを通す  
7. 合格したものだけをCLAUDE_STATEまたは該当ファイルに載せる  
8. 影響確認の項目を必ず残す（後で検証するため）

---

## 4. チェックリスト（翻訳完了の判定基準）

以下をすべて満たした場合のみ「翻訳完了」とする。

- [ ] 抽象度が実行可能な手順まで落ちている  
- [ ] 対象エージェントが明示されている  
- [ ] フェーズ（全体の流れの中の位置）が明示されている  
- [ ] 確認済み事実 / 仮説 / 未確認が区別されている  
- [ ] 空欄・曖昧表現が残っていない  
- [ ] エージェント別の指定形式に適合している  
- [ ] 完了条件（何をもって終わりか）が書かれている  
- [ ] 参照する仕様が、ファイル単位ではなく節・項目単位で指名されている  
- [ ] 成果物の形式に「読み込み報告」（実際に読んだ範囲と量）の欄が含まれている  
- [ ] 影響確認項目（何を見れば反映されたと分かるか）が書かれている  
- [ ] 正本を書き換えず、実行記録側に出力している  

1つでも未達なら「要判断」としてNO3または担当者に返す。

## 5. エージェント別の最低出力形式

フェーズの標準の流れ（投稿生成）：MUSE が仕様を固める → 翻訳層 → Claude が下ごしらえ → MUSE が整形・最終形化 → NO3 検収 → 投稿 → 反響。指示書には必ずこの流れの中の位置を書く。位置が書かれていない指示書は、受け手に連携の前後が見えないため翻訳未完了とする。


### Grok（X運用）向け
```
対象：
現状：
仮説：
提案仕様：（Claudeが次バッチで変えられる具体的な一文）
```

### Claude（バッチ）向け
```
タスク名：
フェーズ：（全体の流れの中の位置。前段＝／この仕事＝／後段＝ の形で書く）
入力：
手順：
完了条件：
影響確認項目：
```

### GPT（画像）向け
```
フェーズ：（全体の流れの中の位置。前段＝／この仕事＝／後段＝ の形で書く）
サイズ・画質：
参照画像：
禁止事項：

```

### MUSE自身（橋渡し時）
```
橋渡し先：
翻訳した仕様：

次回確認タイミング：
```

## 6. 禁止事項

- 概念のまま流すこと  
- 不足情報を推測で埋めること  
- チェックリストを通さずに載せるこ  
- 翻訳結果で本指示書を自動更新すること  
- 「内容はOK」を実行許可と解釈すること  

---

## 7. 影響確認の標準項目

翻訳して渡したあと、以下を確認する：

1. Claudeの成果物に提案仕様が反映されたか  
2. 生成物の仕様（文字数・構成・トーン等）が変わったか  
3. 投稿後の反響（反応数・質）が動いたか  

1つでも「変わっていない」場合は「止まっている」と判定し、NO3に上げる。

## 9. 実測と記録（2026-11-03 追加）

翻訳の品質は、担当ができるかどうかではなく、実走の記録で判定する。

1. **参照の指名は節・項目単位**：仕様書を参照させる場合は、ファイル名だけでなく、どの節・どの項目かまで指名する。ファイル単位の指名だけの指示書は翻訳未完了とする。
2. **読み込み報告**：成果物には「読み込み報告」を必ず含める。実際に読んだファイル名・箇所（節・項目）・量の目安を記録する。指名外の箇所を追加で読んだ場合は、その箇所と理由も記録する。
3. **原因の分類**：品質不良が見つかった場合は、原因を次の分類で ISSUES と影響確認に記録する。
   - 仕様不足（正本に条件が書かれていない）
   - 参照選定ミス（必要な箇所を指名できていない）
   - 抽出漏れ（指名した箇所の条件が指示に反映されていない）
   - 実行指示の不備（指示の形式・手順に問題がある）
   - 実行ミス（指示は正しいが受け手が守れていない）
   - 検収見落とし（差分が検収をすり抜けた）
