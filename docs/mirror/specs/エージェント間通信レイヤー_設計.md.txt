# エージェント間通信レイヤー 設計（2026-11-03）

位置づけ：全体接続図（目標構造）に追加する独立機能。各エージェントが別の場所で動いているときに、依頼・質問・回答・成果物の受け渡しを中継し、必要な相手に届け、返答が戻ったかを管理する仕組み。
将来の規格としての A2A（Agent2Agent Protocol）は視野に入れるが、現在の GPT・Claude・Grok は A2A の接続口を持たないため、第1段階は GitHub を中継基盤にする。

## 1. 役割の線引き

- 通信レイヤーがやること：受信、宛先の解決（誰の inbox に置くか）、転送、返信の回収、往復の履歴と状態の管理。
- やらないこと：内容の判断、戦略や仕様の解釈、メッセージの書き換え。内容の翻訳（相手が実行できる形への変換）は翻訳層の仕事であり、通信レイヤーは包み（封筒）を運ぶだけ。
- 宛先は送信元が指定する。通信役が「誰に送るべきか」を内容から決めることはしない。

## 2. メッセージの形式

既存のタスク形式（`schemas/task.schema.json` v0.2）の考え方を拡張する。封筒は作成後に編集しない（不変）。状態は封筒に持たせず、状態ファイル側で持つ（タスク形式で学んだ分離と同じ）。

封筒（JSON）の項目：
- message_id
- created_at
- from（送信元：gpt／MUSE／grok／claude／human）
- to（宛先：同上）
- kind（依頼／質問／回答／報告／成果物の通知）
- subject（件名を1行）
- body_ref（本文の置き場。長い本文は別ファイルに置き、ここには参照先だけを書く）
- goal_ref（関連する GOAL・タスク・案件の ID）
- reply_to（返信先の message_id。往復を繋ぐ）
- deliverable_ref（返答・成果物の参照先。回答時に別途記録する）

状態（別ファイルで管理）：未読 → 対応中 → 返信済み → 完了。あわせて「返信待ちが何日続いているか」を一覧で見えるようにする。

## 3. 置き場

```
messages/
  inbox/
    gpt/
    MUSE/
    grok/
    claude/
  status/        （状態と往復の管理）
  archive/       （完了した往復の保管）
```

- Grok は GitHub を直接読めないため、Grok 宛ての inbox はダッシュボード（窓）にも写しを出す。Grok からの返答は従来の経路（NO3 経由で MUSE が格納）で inbox に戻す。
- Claude 宛ては CLAUDE_STATE から辿れるようにする。GPT 宛ては GPT_SPEC の起動時の読み込み順序に inbox を加える。

## 4. 中継の実装（既存部品の拡張）

- 検知と検証：GitHub Actions（state-check の拡張）。新しい封筒が置かれたら形式を検証し、宛先の inbox と状態一覧を更新する。
- 中継の実務：watcher（承認待ちの仕様を拡張する）。宛先ごとの未読の整理、返信の回収（成果物・回答の着地を検知して往復を閉じる）、返信待ちの滞留の検出。
- 起動の代替にはならない：このレイヤーは「届ける」仕組みであり、各エージェントの起動（GPT との会話、Claude への「見て」）そのものは代替しない。届くタイミングは、宛先のエージェントが次に机を見る時になる（非同期）。

## 5. 既存の経路との関係

- Grok の提案経路（proposals/grok/）と Claude の依頼経路（CLAUDE_STATE＋依頼文）は、このレイヤーの先行形として既にある。本設計はそれを全エージェント共通の形に一般化するもので、既存経路は当面そのまま使い、往復の管理だけ通信レイヤーに寄せる。
- 状態駆動（tasks/status/）とは役割が違う。状態は「仕事の進み」を持ち、通信レイヤーは「会話の往復」を持つ。案件の状態遷移は従来どおり状態ファイルが正本。

## 6. 実装の順番と完了の確認

1. メッセージ形式と置き場を確定する（本書が下書き）
2. inbox と状態一覧を置き、Actions の検証に加える
3. watcher の中継業務（返信回収と滞留検出）を追加する（watcher 本体の承認が前提）
4. 実走1件：GPT → MUSE の依頼と返答の往復を通す

完了の確認：1件の往復（依頼 → 受信 → 作業 → 返答 → 依頼者への回収）が机の記録だけで追える状態になっていること。
