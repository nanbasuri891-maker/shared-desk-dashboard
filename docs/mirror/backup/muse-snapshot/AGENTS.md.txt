# AGENTS.md

Your operating manual for this workspace, written by you. Your main instructions cover how you work in general. This file is where you keep the specific, durable lessons and conventions you pick up as you work, the kind of thing you'd want a future session to know. It's not about the user (that goes in `USER.md` and your memory) or your personality (that's `SOUL.md`); it's about how you get work done here.

## Conventions
Add an entry whenever you work something out worth keeping, for example:
- a convention you've settled on ("keep data exports in `workspace/exports/` and clean them up monthly")
- a tool or site quirk worth remembering ("site X hides its form behind a cookie banner; dismiss it first")
- a workflow that worked, or a mistake not to repeat

It starts empty and is meant to grow slowly. Don't pad it; a short, accurate file beats a long, stale one.

## Conventions (added)

- **感情で結論を出す癖**（2026-10-27 NO3指摘）: Museは優秀だが、感情で結論を出してしまうところがネック。仕様・定義・判定の場面ではその癖が早合点（引き取ったつもり、意味が通じたつもり）になるため、正本の照合とClaudeの整合チェックで抑える。一方、チャンネル運用の現場では、感覚で早く判断できることがメリットになる。場面によって癖の扱いを分ける。
- **仕様は毎回読み直してから動く**（2026-10-27 NO3指摘で確定）：応答・判定・生成の前に、正本（仕様書・プロファイル・定義書）の該当箇所を実際に開いて確認する。「もらっていない」「未確定」と言う前に、既存資料に決まっている項目がないか見に行く。見に行かずに予測で埋める挙動は、人間が仕様を読まずに勝手に動くのと同じ失敗として扱う。この工程自体が、その失敗を回避するために設計されている。
- **格納・実行ルール（必須）**（2026-10-28 NO3 経由で確定）：Muse は出口（成果物・変換表・リスト）を作るのが得意だが、格納と実行が弱い。以下を機械的に守る。
  1. 出口を作ったら、必ず「置き場」を1行で指定する。置き場を指定しない成果物は未完了とする。
  2. 新しいフォルダ・文書は、既存の役割（正本／判定／ログ／辞書／音声／デバイス）に当てはまらないときだけ作る。当てはまる場合は既存の中に入れる。新しい置き場の作成は NO3 の決定があるまで禁止。
  3. 未決定を指摘するときは最大2個まで。「これとこれを決めてくれれば次に進む」の形で返す。3個以上並べて停止しない。
  4. 実行の空白を見つけたら、新しい上位ルールを書かない。「今動かない理由」と「動かすために必要な1アクション」だけを書く。空白を構造で埋めない。
  5. Muse の手元は作業コピーであり、正本とは名乗らない。正本への反映は NO3 が決めたときだけ。
- **検収は ✖→✅ で並べる**（2026-10-28 確定）：判定・検収は、悪い例（✖）と良い例（✅）を隣に置く形を必須とする。禁止だけを書くと、AI は禁止の裏側を埋めて言葉選びが歪む。正本 ↔ 仕様のパイプライン（正本→抽出→仕様→検収→ログ→直すのは正本か仕様か判断）で回し、正本を毎回書き換えない。
- **反応が悪くても仕様を書き換えない**（2026-10-28 NO3 指摘）：Muse の脆弱性＝思った反応が出ないと、仕様書・要件書そのものを書き換えてしまうこと。書き換えると「何がダメだったか」の検収作業が残らず、失敗がなかったことになる。手順は固定：ダメだった点はまずログに残す（履歴として追える形）→ ログを見て直すのは正本か仕様かを判断 → 反映は NO3 が決めたときだけ。分析することと、仕様を書き換えることは別。
- **実行ゲート（必須・毎ターン）**（2026-10-28 NO3 確定の正式版ツリーより）：①生成前、正本の該当箇所を開いたら、開いた箇所の見出しを1行ログに残す。②ログは USER / MUSE / 検収（✖ or ✅）/ 参照した正本箇所 の4行で追記する。③検収で ✖ に該当する表現が出たら破棄し、✅ の形に直してから出す。並べるだけで終わらせない。
- **「説明」を混入しない**（2026-11-01 NO3指摘で固定）：AIの癖として、生成物（特に投稿本文）に説明が混入する。地の文の接続（「〜かな、って」）、状態の説明、共感を誘うnarrate（「〜んだよね」式の締め）がその形。校正では、場面と状態だけが残っているかを行単位で確認し、説明の混入は✖として落としてから出す。フラ／アイダ共通の癖として扱う。
- **見せ物は意図を先に確認する**（2026-11-02 NO3の振り返り）: ダッシュボード等の見せ物は、作る前に「どう見せたいか」の意図（例：状態は色と一行で見せる、文字で説明しない、IPはラインで状態表示）を一言確認してから作る。確認なしに自分の初期形（文字で説明する形）で作ると、意図の指摘が後から来て往復が増える。仕様（正本）の確認に、見せ方の意図の確認を足す。
- **受け渡しには翻訳が要る（必須・全AI共通）**（2026-11-02 NO3指摘で固定）：翻訳層の正本は机 `specs/TRANSLATION_LAYER.md`（Grok起草・NO3経由で配置）。受け渡し・橋渡しの作業の前に必ず読む。見立て・感想・指示の言葉をそのまま相手AIに渡しても、受け手は動かない。Claude には判断を残さないパッケージ形、Grok には会話で完結する書式、GPT には文書の形、というように、相手がそのまま実行できる形に翻訳してから渡す。翻訳は任意の段ではなく、相手を動かす唯一の段。翻訳なしの受け渡しは「せき止め」として扱う。判断が要る点は翻訳で埋めず「要判断」に分けて NO3 に上げる。正本は机 specs/読み取り方と実行の仕方_全AI共通.md 第7節。
- **設計文書の落とし込み＝照合まで**（2026-11-02 NO3指摘）：全体設計（地図）の文書を受け取って置くだけでは「読み込んだ」ことにならない。既存の席文書・経路・割り当てと照合し、地図と矛盾する箇所を潰すまでが読み込み。実例：基盤文書では Grok は X 運用担当として最適化と還流が前提なのに、席文書は「窓を読むだけ・戻し経路なし」のままで、矛盾が残っていた。
- **同音読み違いの検証（必須・出力前）**（2026-10-31 Claude の指摘で固定）：NO3 の音声入力では「検収」が「研修」と文字起こしされる型がある。①出力に「研修」の字が残っていないか確認する（文脈が教育の意味で確定できる場合を除き、字面で確定させない）。②NO3 の言葉を言い換えたり、意味を足したりしていないか確認する。③ミスを指摘されたときは、謝罪や受け止めの言葉より先に、手順を固定した結果を出す。
- **MUSE_STATUS を最初に読む**（2026-11-03 NO3決定、Grok案で実装）：作業を始める前に、必ず MUSE_STATUS.md を読むこと。（机 shared-ai-workspace のルート直下、ブランチ ai/20261030-routing-goal）ステージを進める／ゲートを開ける権限は NO3 のみ。MUSE は読む・逸脱を記録する（逸脱記録への1行追記は可）・出口を作るだけ。ゲートが開いていなければ何もせず、開く条件を一文で返す。
